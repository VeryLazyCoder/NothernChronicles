# Подробный TODO: Java backend своими руками

Здесь нет готовой серверной реализации: задача — написать её и понять каждое решение. Этапы расположены так, чтобы сначала освоить Java и правила, затем Spring и сеть, затем надёжность и БД. Каждый этап заканчивается проверяемым результатом. Не начинайте рейтинг или регистрацию раньше первой партии между двумя браузерами.

## Этап 0. Окружение и первое приложение

- [ ] **Создать Maven-проект в `backend/`.** Выберите Java 21, совместимую стабильную Spring Boot, зависимости Spring Web, WebSocket, Validation. Сгенерируйте Maven Wrapper. Не добавляйте JPA и Security до понимания их роли; Security для cookie/CSRF и endpoint-политик подключите перед реальным сетевым использованием.
- [ ] **Зафиксировать версии.** Запишите в backend README версии JDK, Boot, Maven, команды запуска Windows/Linux, порт 8080. Используйте Boot dependency management, не выбирайте вручную несовместимые версии Jackson и Spring.
- [ ] **Добавить профиль local.** Разрешённый frontend-origin вынесите в конфигурацию. Начните с `http://localhost:5173`. Не храните секреты в application.yml.
- [ ] **Проверить пустой проект.** Запустите `mvnw.cmd test` и `mvnw.cmd spring-boot:run`, убедитесь, что сервер стартует. Создайте Git-репозиторий и первый коммит.

Критерий: проект собирается с нуля одной командой; вы можете объяснить отличие Maven dependency и Spring bean. Frontend уже отдельно запускается через `npm start`.

## Этап 1. Чистая предметная модель

- [ ] **Создать enum.** Row, CardType, MatchPhase, RoomStatus и ErrorCode. Не используйте произвольные строковые значения внутри домена.
- [ ] **Разделить шаблон и экземпляр карты.** CardDefinition описывает силу/ряд, CardInstance имеет уникальный instanceId и ссылку cardId. Две карты warden в руке — разные экземпляры; команда выбирает одну конкретную.
- [ ] **Перенести каталог.** Создайте resources/cards.json с теми же 14 cardId и значениями из cards.js. При старте сервера проверьте уникальность cardId, допустимые типы/ряды, положительную силу бойца. Не принимайте каталог из browser payload.
- [ ] **Собрать фиксированную колоду.** 24 обычных бойца + 1 герой + 5 спецкарт, всего 30. Генерируйте уникальные instanceId для каждого игрока и матча. Пока не нужен редактор колод и произвольный пользовательский deck.
- [ ] **Создать PlayerState и MatchState.** Следуйте архитектуре: два игрока, три ряда у каждого, рука/колода/сброс, lives, passed, weather, horns, ready, results, revision. Определите, какие поля неизменяемые.
- [ ] **Описать инварианты.** Каждый экземпляр находится ровно в одной зоне; lives 0..2; не больше одного рога на ряд; нет неизвестных cardId; очередь принадлежит участнику; размер колоды не меняется сам по себе.
- [ ] **Передавать генератор случайности снаружи.** Реализуйте Fisher–Yates без повторов. В тестах используйте фиксированный seed, в игре — серверный генератор. Проверяйте сохранность состава, а не «идеальную случайность» на десяти запусках.

Критерий: JUnit-тест создаёт матч с 10/20 картами у каждой стороны и 60 уникальными экземплярами; domain не зависит от Spring. Полезная тема Java: record, enum, List/Map/Set, equals/hashCode, defensive copying.

## Этап 2. Правила и расчёт силы

- [ ] **Написать ScoreCalculator.** Расчёт одного бойца → ряда → стороны. Герой не изменяется; погода сводит обычного бойца к 1; рог удваивает значение после погоды. Сила вычисляется, не принимается от клиента.
- [ ] **Написать start().** Две жизни, round=1, PLAYING, revision=0, руки по 10, пустое поле/эффекты/сброс. Online-стартового игрока выбирайте на сервере.
- [ ] **Ввести доменные команды.** PlayCard(instanceId, row), Pass, ReadyNextRound. Транспортные requestId и cookie домену не нужны; actor передаётся явно из доверенного application-слоя.
- [ ] **Проверять команду до мутации.** Нельзя менять состояние на неверной фазе, чужом ходе, чужой карте, неверном ряду или повторном эффекте. Верните типизированную RuleViolation, а не NullPointerException.
- [ ] **Реализовать UNIT.** Найдите экземпляр только в руке actor, проверьте фиксированный row, переместите на свою сторону, переключите очередь.
- [ ] **Реализовать погоду/CLEAR/HORN.** Погода общая, сыгранные погодные карты сразу в discard; CLEAR очищает общие эффекты; HORN хранится в своём ряду до конца раунда. Повторный рог/погода и CLEAR без погоды не расходуют ход.
- [ ] **Реализовать PASS.** passed сохраняется до конца раунда. Если второй уже спасовал, активный игрок продолжает несколько ходов. Нулевая рука автоматически означает пас.
- [ ] **Написать тесты расчётов.** Два бойца 4 и 6 + герой 10: 20 без эффектов, 12 под морозом, 14 под морозом и рогом, 30 после ясного неба при роге. Рог на одной стороне не меняет другую. Погода не влияет на другой row.
- [ ] **Написать тесты отказов.** Неверная команда оставляет побайтово/структурно то же состояние и revision. Проверьте PLAY_CARD с cardId вместо instanceId, чужим экземпляром, null row у UNIT и неизвестным enum.

Критерий: полноценный ряд ходов работает в JUnit без HTTP и WebSocket. Сверьтесь с `tests/game.test.js` как с примерами спецификации, но реализацию Java напишите самостоятельно.

## Этап 3. Раунды и исход матча

- [ ] **Однократно завершать раунд.** При двух пасах посчитать обе стороны и записать RoundResult. Не завершать повторно при дубликате команды или повторном callback.
- [ ] **Учесть ничью.** Обе стороны теряют жизнь одновременно; обе с нулём → MATCH_OVER с winnerId=null. Нельзя выбрать первого игрока победителем только потому, что проверка его lives идёт первой.
- [ ] **Реализовать ROUND_OVER.** Сохраните поле для UI, activePlayerId=null, ждите по READY_NEXT_ROUND от каждой стороны. Повторная готовность новым requestId — ошибка.
- [ ] **Очистить стол при второй готовности.** Бойцы и рога → discard, weather/ready → пусто, passed сбрасывается с учётом пустой руки, round+1. Руки не добираются. Победившего/проигравшего определяйте по прошлому RoundResult до очистки.
- [ ] **Выбрать старт следующего раунда.** Проигравший начинает; при ничьей стартовавший в прошлом раунде меняется. Если рука пуста, ход получает другой. Если обе пусты, завершите новый раунд 0:0 без зависания.
- [ ] **Завершить матч.** При нулевой жизни больше не принимать игровые действия; сохранять финальную проекцию для RESUME. Добавьте доменный outcome отдельно для будущего abandoned/forfeit, не подменяйте им обычные RoundResult.
- [ ] **Покрыть сценарии JUnit.** Две победы одной стороны; по одной победе и третий раунд; ничья первого; две ничьи; оба без карт; один без карт; повтор PASS/READY после завершения; максимум три раунда.

Критерий: консольный/тестовый сценарий полностью доигрывает матч. Генеративный прогон многих партий сохраняет 30 экземпляров каждого игрока и не создаёт отрицательные жизни.

## Этап 4. Комнаты и гостевые сессии

- [ ] **Реализовать POST /api/session.** Сервер генерирует playerId и session identity, сохраняет в HTTP session и ставит HttpOnly cookie. Существующая cookie сохраняет playerId. Проверить nickname 2–24 символа после trim. Никаких playerId из body.
- [ ] **Продумать cookie/CORS.** В local используйте точный localhost-origin и credentials, обработайте preflight. Для production — HTTPS, Secure и same-origin размещение. Не отключайте всю защиту ради первой успешной сессии; настройте endpoint и CSRF-политику осознанно.
- [ ] **Написать RoomService.** CREATE_ROOM выдаёт уникальный код; JOIN_ROOM проверяет срок/вместимость/занятость гостя. Код 4–12 латинских букв/цифр верхнего регистра. Храните индекс code→roomId и membership playerId→roomId/matchId.
- [ ] **Сделать присоединение атомарным.** Два конкурентных JOIN_ROOM на последнее место дают ровно одного нового участника. Создание MatchState при втором игроке происходит ровно один раз.
- [ ] **Добавить уборку.** Пустая/одиночная WAITING-комната истекает, например, через 10 минут. Удаляйте membership и code-index вместе. Политику перехода гостя после завершения матча опишите явно.

Критерий: unit/integration-тесты проверяют двух игроков, отказ третьему, запрет играть с самим собой и гонку двух присоединений. Разные вкладки с одной cookie — один игрок.

## Этап 5. WebSocket endpoint и DTO

- [ ] **Поднять raw /ws.** Используйте Spring WebSocketHandler/TextWebSocketHandler. Нативный клиент не понимает STOMP/SockJS. Зарегистрируйте только нужный allowed origin.
- [ ] **Привязать identity на handshake.** Получить действующую HTTP-сессию, сохранить доверенный playerId в server-side атрибутах. Отсутствующую сессию отклонить, не доверять имени из JSON.
- [ ] **Описать DTO конверт.** protocolVersion, requestId, type, matchId, expectedRevision, payload. Проверить типы, обязательные поля, enum и размер до обращения к engine. Jackson не должен неявно превращать произвольные строки/дроби в корректные значения.
- [ ] **Написать CommandRouter.** Он направляет комнатные команды в RoomService, игровые — в MatchService; формирует безопасные ERROR с исходным requestId. Стек пишется только в серверный лог с correlation ID.
- [ ] **Сделать SessionRegistry.** playerId→актуальный socket. Новый сокет заменяет старый; onClose старого не удаляет новый. Отправки в одну сессию сериализуются.
- [ ] **Сделать PlayerViewMapper.** Не сериализовать MatchState. Своя рука видна, чужая только счётчик; порядок deck не выдаётся ни одной стороне. Снимки двух игроков различаются viewerId/hand, а открытая часть совпадает.
- [ ] **Реализовать ответы без ACK.** CREATE_ROOM→ROOM_STATE; успешная игровая команда→SNAPSHOT инициатору с его requestId и второму с null; ошибка→ERROR. Начало матча→две проекции. Все поля строго по PROTOCOL.md.
- [ ] **Проверить секреты тестами JSON.** В чужом DTO нет hand/deck/seed, в log нет скрытых карт; у своего есть hand и её размер совпадает с handCount. Пропуск поля проверяйте и после RESUME, и после ERROR/дубликата.

Критерий: кнопка подключения frontend создаёт сессию и открывает сокет, создаётся комната, второй браузер начинает матч. При несовпадении схемы исправляйте DTO по протоколу, а не подставляйте произвольный mock в UI.

## Этап 6. Конкурентность, revision и повторы

- [ ] **Сериализовать изменение одного матча.** per-match ReentrantLock либо однопоточная очередь на матч. Не создавать бесконечный поток на каждый матч; для очередей используйте управляемый executor. Выбор и его ограничения запишите.
- [ ] **Ввести optimistic revision.** После дедупликации сверять expectedRevision. Успех увеличивает revision ровно на один; отказ/RESUME не увеличивает. STALE_REVISION→ERROR и затем актуальный SNAPSHOT инициатору.
- [ ] **Добавить dedup-cache.** Ключ playerId+requestId, fingerprint содержимого. Повтор той же команды возвращает текущую проекцию без мутации; другой payload под тем же ID — REQUEST_ID_REUSE. Дедупликация до revision-проверки. Ограничить размер/срок кеша.
- [ ] **Сохранить порядок публикации.** Под lock подготовьте проекции и поставьте сообщения в упорядоченную очередь. Не допускайте ситуации, когда revision=8 отправлен до revision=7 из другого потока.
- [ ] **Проверить частичные отказы.** Если socket.send упал после сохранения хода, состояние не откатывается. Если socket умер до ответа, RESUME возвращает принятый ход. Доменные ошибки не меняют карту/жизнь/очередь.
- [ ] **Написать конкурентные тесты с барьером.** Две команды одной revision → максимум одна мутация; два одинаковых requestId → одна; две готовности могут дать STALE_REVISION второй стороне, которая затем повторит действие на новом снимке.

Критерий: двойной клик/два сокета/повтор JSON не играют карту дважды. Вы можете объяснить, почему одного ConcurrentHashMap недостаточно и почему нельзя дедуплицировать после применения команды.

## Этап 7. Полная интеграция готового frontend

- [ ] **Запустить фронт на 5173 и Java на 8080.** Использовать localhost в обоих адресах. Открыть обычный и приватный браузер; ввести разные имена.
- [ ] **Пройти комнаты.** Первый создаёт, копирует код, второй входит. У обеих сторон матч, каждая видит свою руку, поля симметричны по смыслу и расположены относительно viewer.
- [ ] **Пройти карту каждого типа.** UNIT во все три ряда; мороз/туман/дождь; CLEAR; HORN; герой. Сила совпадает с Java-тестами. Нельзя сыграть в чужой ряд.
- [ ] **Пройти пас и готовность.** Пас запретил действия, второй продолжает; оба паса завершают раунд; одна готовность не запускает следующий; две запускают без добора.
- [ ] **Пройти проигрыш/ничью.** Две потери жизней завершают матч, без дополнительного игрового хода. Результат и activePlayerId одинаковы для обеих сторон.
- [ ] **Проверить network frames.** В DevTools видеть raw JSON v1, requestId ответов, монотонную revision; не видеть чужой hand или deck. Ошибочные команды тестировать WS-клиентом/интеграционным тестом, UI часть ошибок предотвращает.

Критерий: два человека могут завершить матч, Java-тесты проходят, фронтенд не исполняет demo-engine для online-ходов. Это минимальная сдаваемая версия сетевого практикума.

## Этап 8. Разрывы и защита от некорректных запросов

- [ ] **Реализовать RESUME.** Проверять участника, возвращать его последнюю проекцию либо лобби; не менять revision, не создавать новый матч. Комната уже могла перейти в матч — тогда вернуть SNAPSHOT.
- [ ] **Сохранять незавершённый матч после разрыва.** Начните с grace period 90 секунд. Новое подключение той же session-cookie восстанавливает игрока и отменяет актуальный таймер. onClose старого сокета не запускает таймер вместо нового.
- [ ] **Обработать timeout хода.** Клиент не знает, принят ли ход, и делает RESUME без повторной отправки. Интеграционный тест должен оборвать сеть после commit, до ответа, и проверить отсутствие второго применения.
- [ ] **Определить технический исход.** Один не вернулся, другой онлайн — forfeit; оба ушли — abandoned. Не расходуйте игровые жизни произвольно. Для текущего UI итог всё равно MATCH_OVER/winnerId; причину добавьте безопасной строкой log, сохраняя отдельное серверное outcome.
- [ ] **Ограничить ресурсы.** JSON ≤16 КиБ, разумные лимиты сообщений/секунду и JOIN_ROOM, предел активных комнат, размер очереди отправки и dedup. Не логировать cookie и закрытые руки. Контролировать длину всех строк на сервере.
- [ ] **Удалять ресурсы.** TTL для завершённых матчей/комнат, кешей, registry, lock и таймеров. Очистка не должна удалить новую комнату или активный сокет по устаревшему callback.
- [ ] **Явно описать refresh.** Текущий frontend не помнит matchId после перезагрузки. Следующая доработка: авторизованный GET `/api/me/active-match` либо сохранение ID и безопасный RESUME. Один ID не является правом доступа.

Критерий: краткий разрыв не теряет матч, задержанный ответ не дублирует карту, приложение не копит бесконечные комнаты. Не обещайте восстановление после рестарта JVM до реализации persistence активных игр.

## Этап 9. База данных после работающей игры

- [ ] **Добавить PostgreSQL, Flyway и Spring Data JPA.** Отдельный local-профиль и, при желании, docker-compose только для БД. Пароль через env, схема через миграции, не ddl-auto=create в рабочем окружении.
- [ ] **Спроектировать историю.** Таблицы и ограничения по ARCHITECTURE.md. Результат, места игроков, раундовые счёты, timestamps, outcome. Договориться, сохраняете ли гостей в players или nickname snapshot в participants.
- [ ] **Сохранить результат транзакционно и однократно.** Ключ match_id исключает дубль. Ошибка БД логируется и повторяется безопасно; уже окончившийся матч не должен внезапно вернуться в PLAYING.
- [ ] **Разделить JPA и домен.** Entity отвечает за сохранение, MatchState — за игровую логику. Не делайте lazy-коллекцию Entity источником расчёта силы в WebSocket-потоке.
- [ ] **Добавить интеграционный тест с реальной БД.** Например, Testcontainers: применить миграции, сохранить дважды, получить один матч и правильные round_results. Проверьте null winner у ничьей.

Критерий: завершённые результаты переживают restart, активные партии пока не обязаны. Отдельный endpoint истории и экран истории — дополнительные задачи, не часть текущего UI.
